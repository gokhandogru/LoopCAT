# LoopCAT translator workflow review — 14 September 2026

This review follows a translator from creating a project and importing a file through editing, using resources, checking quality, and exporting. The reported Windows screenshots were the starting evidence. The inspection used the production renderer on Windows, the existing representative translation fixture, and automated interaction plus visual capture at 1440×900, 1366×768, and 1024×768. Additional layout and keyboard checks cover 768×768.

## Findings and changes

| Workflow | Finding | Result |
| --- | --- | --- |
| Navigate the workspace | A long unbroken save-conflict message competed with navigation for horizontal space and wrapped the upper-right controls. | Operation/error notices occupy a separate wrapping strip below navigation. They no longer change the header height or move its controls. |
| Understand saving | Routine saving messages interrupted typing, and the green style made an error look successful. The dark theme also classified every save notice as success. | Routine autosave notices are silent; actionable persistence errors remain visible. Error styling uses the danger palette in light and dark themes. Workspace retains detailed local-save and external-backup information. |
| Import and synchronize | Resource migration during an import could leave the initialization notice visible after completion, masking the final validation result. Backup I/O errors also appeared as file-validation reports. | Migration clears its own notice on completion or failure, including imports after startup. ## Workflow inspection

- **Project setup:** the Projects dashboard has one New project action. The dialog exposes language selection and optional resources without requiring AI configuration. The guide explains the shortest create/import/edit/QA/export route.
- **File handling:** project and editor import entry points remain discoverable. Import panels stay within the editor. Validation errors retain a dismiss action. Format correctness, checkpoint/archive compatibility, save races, and performance are covered by the separate import/export and persistence fixes and their regression tests; visual inspection alone cannot establish file fidelity.
- **Translation:** confirmation stays prominent, source and target remain the main surface, and Next unconfirmed remains directly available. Compact density, Focus mode, and hiding the inspector offer more editing space without changing the document.
- **Resources and review:** contextual Matches, Quality, Review, AI, and Info tabs prevent all inspector functions appearing at once. The existing capture covers TM and termbase catalogs, resource deletion/restoration, review comments, quality workbench, contextual AI, and provider settings.
- **Delivery and recovery:** Export remains a primary editor menu; folder copies and backup operations remain in Workspace. The UI distinguishes local persistence from external recovery copies rather than calling both simply “saved.”

## Evidence and limits

The updated baseline captured **87 screens** across the three desktop viewports. Source and target together occupy **61.91%** of the 1366px workspace with the inspector open and **85.33%** with it closed. Additional assertions verify that a long error does not displace navigation, the inspector aligns with the workspace, hidden controls remain hidden, and advanced-menu state/keyboard focus behave correctly. Twelve menu and workspace unit tests, CSS lint, formatting, and locale validation passed during this review.

Final capture evidence is in `test-artifacts/ux-review-20260914-final/`, with measured geometry in `baseline.json`. The complete 87-screen pass was repeated after the control-width refinement. Visual inspection confirms that document, search, search options, replacement, segment status, Filters, and Next unconfirmed fit on one row at 1366px.

This is a code and interaction review, not a claim that every translator preference or assistive-technology combination has been validated. Native macOS/Linux execution, NVDA/VoiceOver sessions, and the full 200% zoom/forced-colors matrix still require their corresponding environments. Long or unsupported source files also need format-specific fidelity checks, not just a clean visual import flow.

## Performance measurements

Windows x64, Intel Core i7-8550U, 16 GiB RAM, Electron 43.3.0 / Chromium 150. The benchmark uses real IndexedDB acknowledgements and 30 synthetic edits per size. Response measures two animation frames, not physical keyboard latency. The 450ms autosave delay is included in save timings.

| Run | Segments | p95 response | p95 input handler | p95 local save | Verified checkpoint | ZIP write |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Full run | 10,000 | 112.5ms | Not separated | 539ms | 8.23s | 2.21s |
| Full run | 100,000 | 76.2ms | Not separated | 524ms | 131.35s | 16.69s |
| Diagnostic repeat | 10,000 | 49.2ms | 2.8ms | 620ms | 7.92s | 2.34s |

The first 10k run missed the existing 100ms response budget; the diagnostic repeat passed without changing production code or relaxing the threshold. Both results are retained in `output/ux-performance-full.json` and `output/ux-performance-diagnostic.json`. This variance prevents claiming a consistent latency improvement. The benchmark now optionally selects 10k records and records input-handler timing for investigations; the default still covers 10k and 100k.

Checkpoint verification and ZIP writing are separate from source-file import/export and normal editing saves. Large workspace backups remain expensive. Bounded batching reduces per-record database round trips and preserves atomic snapshots, but it does not make a 100k-record full backup instant. A multi-hour soak and native checks on other operating systems are still needed before production qualification.
